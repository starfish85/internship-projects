# 爬取策略：约 41 万酒店 · 分期分批

## 1. 为什么不能“一次扫完”

| 因素 | 影响 |
|------|------|
| 量级 ~410,000 | 全量列表 + 详情 + 日历价 = 百万级请求 |
| 日历价 | 若 90 天 × 每店，请求量再放大一个数量级 |
| 前端同源 API | 依赖登录 token，需限速与会话保活 |
| 磁盘与温度 | 连续写入外接 SSD，需监控 |

因此默认策略是：**目的地分片 → 酒店分页 → 详情/语言 → 日历窗口 → 外接盘批次落盘**。

## 2. 分层数据模型

```text
Destination (CN city / dest code)
  └── Hotel (hotelCode)          ← 主键匹配中英文
        ├── ContentZH / ContentEN
        └── CalendarRate[]       ← hotelCode + checkIn + nights + board/rate
```

**匹配原则**

- 主键：`hotelCode`（或 API 明确的 supplier hotel id）
- 禁止：仅用酒店中文名 / 英文名模糊匹配做合并
- 次要键：GIATA / 坐标（若接口提供，用于校验）

## 3. 分期计划

### 阶段 A — 探针（本阶段，已部分完成 2026-07-27）

- [x] 登录 + `darwinToken`（Bearer）
- [x] 酒店 Tab / 搜索表单选择器
- [x] FTS 列表接口（中英 + 目的地）
- [ ] 详情 content path（仍 404）
- [ ] 日历价 avail path（仍 404，需 UI 成功搜索后抓包）
- 详见 `docs/API探测记录.md`

### 阶段 B — 单城市样例（如北京）

- `maxHotels=20~200`
- 落 `batches/CN/by-city/北京/<runId>/`
- 验证中英字段与 7 日日历窗口

### 阶段 C — 目的地覆盖

- 从目的地下拉 / 目的地 API 枚举中国大陆城市
- 写 `state/cn-destinations.json`
- 按优先级：一线 → 省会 → 其他

### 阶段 D — 全量批跑

- 每城一目录或每 N 店一切片
- `checkpoint.json` 记录：当前 dest 索引、page offset、失败队列
- 日历：默认未来 90 天，按 7 天窗口滑动（可配置）

## 4. 批次与文件格式

推荐 **JSONL**（一行一条，便于追加与崩溃恢复）：

```json
{"hotelCode":"123","nameZh":"...","nameEn":"...","destCode":"PEK","capturedAt":"..."}
```

```json
{"hotelCode":"123","checkIn":"2026-08-01","nights":1,"board":"RO","price":"...","currency":"CNY"}
```

每批结束写 `meta.json`：`count`、`errors`、`apiVersion`、`runId`。

## 5. 限速与会话（gentle-xhr，2026-07-28 起）

**原则：不刷 SPA UI、不并发抢同一标签页、纯 XHR + 长间隔。**

| 参数 | 默认（pipeline.json） | 说明 |
|------|----------------------|------|
| list `ftsSize` | 2000 | 单次 FTS 上限（旧 100 会漏店） |
| list `requestDelayMs` | 1200 | 关键词之间间隔 |
| list `destPauseMs` | 2500 | 城市之间休息 |
| list `mergeExisting` | true | 重拉只扩不缩 |
| product `batchSize` | 8 | detail 批量（旧 20 偏猛） |
| product `requestDelayMs` | 1500 | 中英 detail 间隔 |
| product `destPauseMs` | 3000 | 城市间休息 |
| calendar `requestDelayMs` | 2000 | 查价更慢 |

启动脚本：`bash scripts/pipeline/run-gentle.sh {list-tier1|enrich-all|status}`

| 历史参数 | 说明 |
|------|------|
| `calendarWindowDays` | 7 | 日历窗口 |
| `calendarDaysAhead` | 90 | 向前覆盖天数 |

会话掉线：`ensureLoggedIn` 重登；连续 401 则停批并告警。

## 6. 外接盘监控联动

跑批前 / 跑批中：

```bash
npm run disk:monitor
```

若 `alerts` 含 `temp_critical` 或 `space_critical`：**暂停写入**，降温或腾空间后再继续。

## 7. 与活动爬取的差异

| 项 | Activities（历史） | Hotels（本项目） |
|----|------------------|------------------|
| 产品按钮 data-qa | `ACTIVITY` | 待探针确认 `HOTEL` |
| 列表 API | `.../activities/availability` | 探针捕获后固化 |
| 主键 | activityCode | hotelCode |
| 价格形态 | 活动单价 | 日历 / 连住价 |

可复用：登录、cookie 弹窗、持久 profile、JSON/CSV 落盘风格。

## 8. 成功判据（试点）

- [ ] 北京（或指定城）≥ 20 家酒店有稳定 `hotelCode`
- [ ] 至少一种中英内容字段可区分或双语接口可合并
- [ ] 至少 7 天日历价样例写入 `calendar.jsonl`
- [ ] 外接盘 monitor 无 critical alert
- [ ] checkpoint 可中断后续跑
