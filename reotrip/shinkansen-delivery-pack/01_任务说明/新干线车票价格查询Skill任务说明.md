# 新干线车票价格查询 Skill 任务说明

## 1. 项目背景

定制游业务中，客人跨地区移动时经常需要购买日本新干线车票。例如客人可能提出“11 月 12 日 12 点左右从东京去金泽”这类需求。为了更快给出报价参考，需要做一个新干线车票价格查询 Skill，帮助从客人需求文本或需求截图中提取查询条件，并在订票网站中查找可购买车次和真实展示价格。

本任务使用 Trip.com 和 Klook 作为查价来源。它不是下单工具，也不是抢票工具，只用于只读查询和整理可售车次价格。

## 2. 任务目标

请完成一个“新干线车票价格查询 Skill”。

Skill 需要支持输入客人需求文本或需求截图，提取以下核心信息：

| 信息 | 说明 |
| --- | --- |
| 出行日期 | 例如 2026-11-12 |
| 出发地 | 例如 Tokyo Station、东京站 |
| 目的地 | 例如 Osaka、Kyoto、Kanazawa |
| 期望出发时间 | 例如 12 点左右；如果客人没写，可以不限制时间 |
| 乘客人数 | 按客人实际需求人数识别，不固定成人或儿童数量 |

查询后需要输出可购买车次，并尽量清晰展示：

| 字段 | 要求 |
| --- | --- |
| 出发时间 | 订票网站真实展示时间 |
| 到达时间 | 订票网站真实展示时间 |
| 出发站 | 订票网站真实展示站点 |
| 到达站 | 订票网站真实展示站点 |
| 列车类型或车次 | 例如 Shinkansen、Nozomi、Hikari 等，以网站实际展示为准 |
| 坐席类别和价格 | 只需要坐席类别和对应真实展示价格 |

价格必须来自 Trip.com 或 Klook 页面真实展示，不允许换算、不允许推算、不允许自己估价。

## 4. 基础任务要求

基础任务必须完成：

1. 支持从文本需求中提取日期、出发地、目的地、期望时间和乘客人数。
2. 支持从需求截图中提取同类信息。Codex 支持视觉识别，因此可以通过 Skill 指引 Codex 读取图片信息。
3. 能使用 Trip.com 或 Klook 查询新干线可购买车次。
4. 能列出符合需求的可购买车次。
5. 能输出每个车次下不同坐席类别的真实展示价格。
6. 价格优先使用 USD，其次使用 HKD。
7. 如果网站没有展示 USD 或 HKD，不允许自行换算；需要说明本次未能取得符合币种要求的价格。
8. 不展示不可订车次。
9. 不强行限制输入范围，只要输入里有日期、始发地、目的地，就应尝试查询合适车次。

Trip.com 和 Klook 不要求基础任务同时完整支持两个渠道。基础任务至少稳定支持一个渠道，另一个渠道可以作为备选或进阶对比来源。但最终说明中必须写清当前支持了哪些渠道、哪些渠道还未实现或不稳定。

## 5. 未开售日期处理规则

如果客人给出的日期未开售，不能随意估价。

处理方式：

1. 优先在未来 2 个月已释放库存日期中，寻找同线路的热门日期作为报价参考，例如樱花季、特殊节假日、周末或明显高需求日期。
2. 其次在未来 2 个月已释放库存日期中，寻找和目标日期同星期几的日期作为报价参考。
3. 参考价必须仍然来自订票网站真实展示价格。
4. 输出中必须明确说明：目标日期尚未开售，本次使用某个已开售日期作为报价参考。
5. 不能把参考价描述成目标日期真实价格。

## 6. 安全边界

本任务必须严格遵守以下边界：

1. 只允许访问 Trip.com 和 Klook 的公开查价页面。
2. 不允许登录未授权账号。
3. 不允许加入购物车。
4. 不允许点击 Book now 后进入会锁票、占座或生成订单的步骤。
5. 不允许填写乘客信息。
6. 不允许提交订单。
7. 不允许进入支付流程。
8. 不允许绕过验证码、风控、地区限制或访问控制。
9. 不允许高频批量请求网站。
10. 不允许修改任何订单、价格、库存、账号或后台数据。

如果某一步需要继续点击才可能看到价格，但该点击会进入下单、锁票或支付流程，应立即停止，并在过程记录中说明卡点。

## 7. 建议实现方式

这个任务更适合做成“查价 Skill / 浏览器自动化查价工具”，不建议做成泛化爬虫。

建议实现路径：

1. 先手动熟悉 Trip.com 和 Klook 的日本铁路购票流程。
2. 观察输入出发地、目的地、日期、乘客人数后，页面如何展示车次和价格。
3. 确认 USD 和 HKD 链接或币种切换方式。
4. 设计 Skill 的输入格式和输出格式。
5. 编写 Skill 文档，例如 `SKILL.md`，说明 Codex 收到文本或图片后应该如何提取需求、如何查价、如何输出。
6. 如有能力，再补充浏览器自动化脚本或辅助脚本。
7. 用测试样例逐条验证，不要只测东京站到大阪站。

建议项目结构：

```text
shinkansen-price-skill/
├─ SKILL.md
├─ README.md
├─ examples/
│  ├─ sample-inputs.md
│  └─ sample-output.md
└─ scripts/
   └─ 可选辅助脚本
```

如果暂时无法完成自动化脚本，基础交付至少要把 `SKILL.md` 写到 Codex 可以按步骤执行查价，并能稳定输出一致格式。

## 8. 输出格式要求

每次查询结果建议按下面格式输出：

```text
需求识别：
日期：2026-11-12
出发地：东京站
目的地：金泽
期望时间：12:00 左右
乘客人数：按客人需求列出

查询结果：
1. 车次或列车类型：以网站展示为准
   出发：12:xx，东京站
   到达：xx:xx，金泽站
   坐席价格：
   - 坐席类别 A：USD xx.xx 或 HKD xx.xx
   - 坐席类别 B：USD xx.xx 或 HKD xx.xx
   - 坐席类别 C：USD xx.xx 或 HKD xx.xx

说明：
目标日期是否已开售；如未开售，说明参考日期和参考原因。
```

正式展示时不需要突出展示来源网站、查询日期、查询时间，但可以在结果数据或过程记录中保留，方便后续核查。

## 9. 交付目标

请将最终文件放入：

```text
03_实习生提交/
```

必交内容：

| 文件 | 要求 |
| --- | --- |
| `shinkansen-price-skill/` | Skill 项目文件夹 |

`交付说明.md` 的三句话格式固定如下：

1. 这个项目实现了什么功能。
2. 这个项目怎么使用，输入是什么或运行命令怎么给。
3. 这个项目还有什么未实现的地方；如果没有，则写“暂无”。

## 10. 测试要求

测试样例是给你自己验证项目是否完善的，不是把每个测试样例的完整查价结果交给负责人。

你需要做的是：

1. 使用 `02_参考资料/测试样例.md` 中的样例逐条测试。
2. 不只测试东京站到大阪站，也要测试东京到京都、东京到金泽、大阪到东京等路线。
3. 检查 Skill 是否能正确识别日期、出发地、目的地、时间和乘客人数。
4. 检查结果价格是否来自网站真实展示，不能换算或推算。
5. 检查不可订车次是否被排除。
6. 如果某个样例明显失败，应先修改 Skill 或说明限制，不要直接交付。
7. 如果做了 HTML 页面，页面样式明显错乱、文字遮挡、价格看不清、移动端明显不可读，都需要先修改再交付。

提交时只需要在 `测试记录.md` 中写总体测试结果，例如：

```text
共测试 8 个样例，通过 6 个，2 个因目标日期未开售使用参考日期逻辑。
发现的问题：Klook 某些城市名称需要英文站点名，已在 Skill 中补充说明。
仍未解决的问题：暂无。
```

不需要把每个测试样例的完整查价结果都交给负责人。

## 11. 验收标准

任务合格标准：

1. Skill 能处理文本输入。
2. Skill 能处理需求截图输入。
3. Skill 能识别日期、出发地、目的地、期望时间和实际乘客人数。
4. Skill 能查到可购买车次，并排除不可订车次。
5. Skill 能展示坐席类别和真实展示价格。
6. 价格优先 USD，其次 HKD，且没有自行换算或推算。
7. 未开售日期能按规则找参考日期，并清楚说明参考原因。
8. 测试样例覆盖多条路线，不只覆盖东京到大阪。
9. `测试记录.md` 能说明总体测试结果和已知问题。
10. 没有执行下单、锁票、支付或修改数据的操作。

## 12. 进阶拓展目标

完成基础任务后，可以选择做以下拓展：

1. 做一个美观的 HTML 查询结果页，用卡片或表格清晰展示车次、站点、时间、坐席类别和价格。
2. 支持 Trip.com 与 Klook 两个渠道结果对比，在结果中标出同一需求下哪个渠道价格更适合作为参考。
3. 增加常见站点名称映射，例如“东京/东京站/Tokyo Station”“大阪/新大阪/Shin-Osaka”“京都/Kyoto”等。
4. 增加错误处理说明，例如城市无法识别、日期未开售、网站无 USD/HKD 价格、页面加载失败时应该怎么反馈。

进阶目标是选做，不影响基础任务验收。
