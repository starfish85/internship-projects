# 采集节奏与风控

采集必须像人在点页面，禁止并行打站、禁止穷举接口、禁止验证码绕过。

## 硬性限制

- 同一时刻只开 **1 个** 浏览器上下文、只操作 **1 个** 前台标签（后台标签保持登录即可）。
- **禁止** `spawn_subagent` 去同时爬 Viator / Tripadvisor。
- **禁止** 对同一域名并发 `web_fetch` / `open_page` / XHR。
- **禁止** 破解、绕过验证码或风控页。出现即停。
- 不要为了快去逆向未在当前页面触发的隐藏 API 并批量轮询。列表页若已自然发出且返回完整数据的 XHR，可以读这一次响应，不要另开循环刷接口。

## 间隔

两次导航 / 搜索 / 翻页之间等待 **8–15 秒**，用均匀随机抖动，不要固定间隔。

每完成 **10 次** 页面加载，额外暂停 **20–40 秒**。

每个产品的 Tripadvisor 核透传：最多 **1 次搜索 + 3 个候选结果页**。搜不到就记「未透传」，不要换一堆同义词狂搜。

## 立刻停止的信号

看到任一情况：**保存 checkpoint → 告诉用户 → 等待指令**，不要重试超过 1 次。

- 登录墙、会话过期、跳到 login / captcha / challenge
- HTTP 403 / 429，或页面含 `unusual traffic` / `are you a robot` / `Access Denied`
- 连续 3 次空白/错误页
- 用户说停止

恢复时从 checkpoint 的下一件未完成项继续，不要从头把已完成的 130 条再点一遍。

## 预估时长（约 130 条已上线产品）

Viator 详情约 30–40 分钟；Tripadvisor 按产品核透传约 50–70 分钟；企业位置页视数量 20–40 分钟。全程可能 2 小时左右。中途必须可暂停。
